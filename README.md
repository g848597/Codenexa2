# Telegram Toolkit — Backend

Реализация Этапа 1 (Core Foundation) из `01-core-foundation.md`. Отдельный
сервис (не часть Codenexa2) — своя схема БД, может временно жить в той же
Supabase, что и CodeNexa (таблицы не пересекаются), либо в отдельной базе.

## Стек

- Python 3.11+, FastAPI, psycopg2 (пул соединений), PostgreSQL 13+
- Авторизация — только через Telegram `initData` (HMAC-SHA256), без пароля

## Структура

```
app/
  config.py          — загрузка .env
  db.py              — пул соединений к Postgres, init_db() применяет миграции
  telegram_auth.py    — проверка подписи initData
  deps.py            — get_current_user (авто-создаёт юзера при первом входе)
  repo.py            — весь SQL: users, projects, brand_kits, generated_items, templates
  modules_registry.json — единый реестр модулей (пока пустой, дополняется на Этапах 2-7)
  api/
    me.py            — GET /api/me
    projects.py       — CRUD проектов
    brand_kit.py      — GET/PUT brand-kit
    history.py        — Smart History (list/create/favorite/delete)
    modules.py         — GET /api/modules (отдаёт modules_registry.json)
    telegram_tools.py — Этап 2: username-checker, bio-generator, deep-link-builder
    utility.py         — Этап 3: url-shortener + публичный редирект GET /r/:slug
  server.py           — точка входа
migrations/
  001_init.sql — DDL Этапа 1 (идемпотентно, IF NOT EXISTS)
  002_utility.sql — DDL Этапа 3: таблица short_links
tests/gen_init_data.py — dev-утилита для ручного тестирования без Telegram-клиента
```

## Запуск локально

```bash
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
cp .env.example .env   # прописать DATABASE_URL и TELEGRAM_BOT_TOKEN
./.venv/bin/uvicorn app.server:app --reload --port 8001
```

Таблицы создаются автоматически при старте (`init_db()` в `server.py`),
отдельно гонять `migrations/001_init.sql` руками не обязательно, но можно:

```bash
psql "$DATABASE_URL" -f migrations/001_init.sql
```

### Тест без Telegram-клиента

```bash
export TELEGRAM_BOT_TOKEN=<тот же токен, что в .env>
INIT_DATA=$(python tests/gen_init_data.py)
curl -H "Authorization: tma $INIT_DATA" http://127.0.0.1:8001/api/me
```

## API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/me` | Текущий юзер (создаёт при первом входе) |
| GET | `/api/projects` | Список проектов |
| POST | `/api/projects` | Создать проект (+ пустой Brand Kit) |
| PATCH | `/api/projects/:id` | Переименовать / сделать активным по умолчанию |
| DELETE | `/api/projects/:id` | Soft-delete (если был дефолтным — флаг переносится на следующий) |
| GET | `/api/projects/:id/brand-kit` | Получить Brand Kit |
| PUT | `/api/projects/:id/brand-kit` | Обновить Brand Kit (upsert) |
| GET | `/api/projects/:id/history` | История (`?module=&favorites=&limit=&offset=`) |
| POST | `/api/projects/:id/history` | Записать результат модуля в историю |
| PATCH | `/api/projects/:id/history/:item_id` | Toggle избранного |
| DELETE | `/api/projects/:id/history/:item_id` | Удалить запись |
| GET | `/api/modules` | Реестр модулей (пока `[]`) |

Все `/api/projects/:id/*` эндпоинты проверяют, что проект принадлежит
авторизованному пользователю (401/404, без утечки чужих данных).

## Этап 2 — Telegram Tools

Реализация `02-telegram-tools.md`. Из 6 модулей раздела серверная логика
нужна только трём — остальные (Markdown Builder, Unicode Fonts, Text
Cleaner) чисто клиентские по спеке, отдельных эндпоинтов под них нет.

| Метод | Путь | Модуль |
|---|---|---|
| GET | `/api/tools/username-checker?username=` | 2.1 Username Checker — валидация формата + запрос к `t.me/<username>` |
| POST | `/api/tools/bio-generator` | 2.2 Bio Generator — шаблонная генерация (без AI), 3 варианта |
| POST | `/api/tools/deep-link-builder` | 2.3 Deep Link Builder — валидация + сборка ссылки |

Результаты Bio Generator / Deep Link Builder / Markdown Builder (по DoD они
пишутся в историю) сохраняются через уже существующий универсальный
`POST /api/projects/:id/history` — отдельного per-модульного эндпоинта не
заводили, `generated_items` рассчитана на любой `module_key`.

`app/modules_registry.json` дополнен 6 записями с `section: "telegram_tools"`.
Форма записи (`key`, `section`, `order`, `title`, `description`, `icon`,
`route`, `backend_endpoint`, `saves_to_history`) — предположение по аналогии
с уже существующими API (`01-core-foundation.md` с точным контрактом
`ModuleConfig` в этот чат не передавался), при появлении фронтенда/спеки
контракта сверьте поля и при необходимости приведите в соответствие.

Username Checker определяет занятость username эвристикой по HTML-маркерам
страницы `t.me/<username>` (`tgme_page_title` / `tgme_page_extra`), так как
у Telegram нет официального метода "проверить свободен ли username" в Bot
API, а страница `t.me` всегда отвечает 200 и для занятых, и для свободных
имён. Это best-effort для MVP — если эвристика начнёт давать ложные
срабатывания, её нужно будет уточнить по актуальной вёрстке `t.me`.

## Фронтенд (Этап 2) — Telegram Mini App

`frontend/` — React + TypeScript + Vite + Tailwind, роутинг через `HashRouter`
(`#/tools/...`), 6 страниц по числу модулей раздела + главная с сеткой карточек.

Запуск локально:
```
cd frontend
npm install
cp .env.example .env   # VITE_API_BASE_URL -> адрес бэкенда
npm run dev
```
Продакшн-сборка: `npm run build` → статика в `frontend/dist`, раздаётся
любым статик-хостингом (сам бэкенд статику не отдаёт — см. CORS выше).

Что где лежит:
- `src/modules.config.ts` — зеркало `app/modules_registry.json`
- `src/lib/telegram.ts` — тема/initData из `window.Telegram.WebApp` (используется
  официальный `telegram-web-app.js`, а не `@telegram-apps/sdk` — см. комментарий
  в файле, почему)
- `src/lib/api.ts` — клиент к бэкенду, включая заголовок `Authorization: tma <initData>`
- `src/lib/markdown.ts`, `unicodeFonts.ts`, `textCleaner.ts` — вся клиентская логика
  модулей 2.4/2.5/2.6, без единого запроса на сервер
- `src/components/ConsolePanel.tsx` — сквозной "консольный" вид результата
  (моноширинный текст + цветная левая полоса = статус), один и тот же во всех
  6 модулях, т.к. результат everywhere — строка, которую копируют

Проверено вручную (см. итоги в чате): `tsc --noEmit`, `vite build`, скриншоты
всех 6 страниц в мобильном вьюпорте (375×812, без горизонтального скролла),
и сквозной прогон через Playwright с реально поднятым бэкендом — ввод формы →
запрос → ответ → консольная панель, для всех модулей с бэкенд-логикой, плюс
клиентские сценарии (тулбар Markdown Builder, чекбоксы Text Cleaner, копирование
в буфер для Unicode Fonts).

**Не проверено** (нет доступа из этой среды): реальный ответ `t.me/<username>` —
в песочнице egress-прокси отдаёт 403 на домен вне allowlist, поэтому Username
Checker проверен только на ветке обработки ошибки; на реальном деплое запрос
пойдёт напрямую. Авторизованные сценарии (initData, сохранение в историю) не
проверялись живьём — нужен реальный Telegram Mini App контекст, а не браузер.

## Этап 3 — Utility

Реализация `03-utility.md`. Зависимость — только Этап 1 (без Brand Kit),
можно было делать параллельно с Этапом 2. Из 6 модулей раздела серверная
логика нужна только одному:

| Метод | Путь | Модуль |
|---|---|---|
| POST | `/api/tools/url-shortener` | 3.6 URL Shortener — создаёт короткую ссылку (base62-слаг, 6 символов) |
| GET | `/api/projects/:id/short-links` | Список сокращённых ссылок проекта с актуальным счётчиком кликов |
| GET | `/r/:slug` | Публичный редирект-эндпоинт (302 на `original_url`, инкремент `clicks`) — без `/api`-префикса и без авторизации, так как по этой ссылке переходят напрямую в браузере, а не из Mini App |

3.1 Password Generator, 3.2 JSON Formatter, 3.3 Base64, 3.4 Timestamp
Converter — целиком клиентские, без единого запроса на бэкенд (по спеке).
3.5 UTM Builder пишет историю через уже существующий универсальный
`POST /api/projects/:id/history` — отдельного эндпоинта не заводили, как и
для модулей Этапа 2. Password Generator по спеке — единственный модуль во
всём тулките, который намеренно **не** пишет ничего в историю: пароли не
должны лежать в БД, это явное секьюрити-требование DoD.

Новая таблица — `short_links` (`migrations/002_utility.sql`):
`id, project_id, original_url, slug (unique), clicks, created_at`.
Слаг — 6 случайных base62-символов (`secrets.choice`, не `random` — чтобы
слаг был непредсказуем), при коллизии (практически невозможной на 62^6
пространстве) перегенерируется до 8 раз. Клики читаются напрямую из
`short_links` (не из `generated_items`, которая хранит только слепок на
момент создания ссылки), поэтому у списка ссылок отдельный эндпоинт.

Домен для `short_url` в ответе API берётся из `SHORT_LINK_BASE_URL`
(`.env`) — по умолчанию совпадает с адресом самого бэкенда, задайте отдельно
при деплое за собственным доменом.

`app/modules_registry.json` дополнен 6 записями с `section: "utility"`
(`order: 1..6`, порядок как в спеке).

## Фронтенд (Этап 3) — 6 новых страниц Utility

Добавлены в тот же `frontend/`, что и Этап 2 — без нового проекта/сборки.
Главная страница (`src/pages/Home.tsx`) теперь группирует карточки по
разделам (`Telegram Tools` / `Utility`) вместо плоского списка.

Новые файлы:
- `src/lib/passwordGenerator.ts` — генерация через `crypto.getRandomValues`
  без modulo-bias (не `Math.random`), оценка энтропии в битах
- `src/lib/jsonTool.ts` — парсинг с извлечением позиции/строки/колонки
  ошибки из текста исключения `JSON.parse` (V8/JSC), форматирование
  (отступ 2/4), минификация, рекурсивная сортировка ключей — без
  react-json-view/CodeMirror, которые упоминались в спеке как вариант:
  подсветка результата переиспользует существующий `ConsolePanel`
- `src/lib/base64.ts` — кодирование/декодирование через
  `TextEncoder`/`TextDecoder`, а не голый `btoa` (падает на кириллице)
- `src/lib/timestamp.ts` — двусторонняя конвертация Unix ⇄ дата
- `src/lib/utm.ts` — сборка ссылки через `URLSearchParams`/`URL` (корректное
  экранирование), автодополнение `source`/`medium` в `localStorage`
  (последние 10 значений каждого поля, без обращения к бэкенду)
- `src/pages/PasswordGenerator.tsx`, `JsonFormatter.tsx`, `Base64Tool.tsx`,
  `TimestampConverter.tsx`, `UtmBuilder.tsx`, `UrlShortener.tsx`

UTM Builder и URL Shortener связаны кнопкой «Сократить эту ссылку»
(react-router `navigate(..., { state })`) — по спеке 3.6 "можно принимать
прямо из UTM Builder одной кнопкой". QR для собранной UTM-ссылки
переиспользует тот же `qrcode`-пакет и паттерн, что уже был в
`DeepLinkBuilder.tsx` на Этапе 2 (спека 3.5 явно на это ссылается:
"если Этап 5 готов — переиспользовать QR-компонент"; отдельного QR-модуля
Этапа 5 в этом чате не было, поэтому переиспользован ближайший рабочий
аналог).

Проверено: `tsc --noEmit` — чисто, `vite build` — чисто, `oxlint` — чисто на
новых файлах (единственное предупреждение в проекте — в уже существующем
`textCleaner.ts` из Этапа 2, к этому этапу не относится). Логика всех
клиентских модулей прогнана смоук-тестом (`tsx`): Base64 роундтрип на

ключей, сборка UTM-ссылки, генерация пароля и оценка энтропии, конвертация
timestamp во все 5 форматов — все сценарии дали ожидаемый результат.
Генерация slug (`secrets.choice`, base62, 6 символов) проверена на
уникальность 20 сгенерированных значений. Авторизованные сценарии (сохранение
UTM в историю, вызов `POST /api/tools/url-shortener`) не проверялись живьём —
как и на Этапе 2, нужен реальный initData внутри Telegram Mini App.

## Этап 4 — Контент

Реализация `04-content.md`. Зависимость — Этап 1 (Brand Kit **обязателен**):
все 6 модулей принимают `tone` и `brand_emojis` как входные данные, фронтенд
подставляет их дефолтом из `GET /api/projects/:id/brand-kit`, пользователь
может переопределить тон перед генерацией.

| Метод | Путь | Модуль |
|---|---|---|
| POST | `/api/tools/post-constructor` | 4.1 Конструктор постов — хук → тело → CTA, тезисы распределяются по секциям |
| POST | `/api/tools/welcome-message` | 4.2 Приветственное сообщение — с плейсхолдером `{name}` под будущего бота |
| POST | `/api/tools/group-rules` | 4.3 Правила группы — нумерованный список из типовых + своих пунктов |
| GET | `/api/tools/group-rules/catalog` | Каталог типовых пунктов правил и типов сообществ (чтобы не дублировать константы во фронтенде) |
| GET | `/api/tools/headline-generator` | 4.4 Генератор заголовков — 3/5/10 вариантов по разным паттернам |
| POST | `/api/tools/cta-generator` | 4.5 Генератор CTA — 3 варианта на цель × тон |
| GET | `/api/tools/hashtag-generator` | 4.6 Генератор хештегов — 5/10/15 по теме и категории |

Без AI в MVP, как и требует спека — весь текст собирается шаблонным
движком `app/content_engine.py` (`generate(template_key, variables)` /
`generate_many(...)`, с сохранением неизвестных плейсхолдеров вроде
`{name}` буквальными). Вся смысловая структура (скелеты постов, банки фраз
CTA, паттерны заголовков, словарь хештегов) — в `app/content_logic.py`,
движок про неё ничего не знает. Когда появится AI Writer, по примечанию из
`04-content.md` эти же функции можно подменить вызовом LLM-API с теми же
`variables`, не трогая роуты (`app/api/content.py`) и фронтенд.

Конструктор постов (4.1) реально переиспользует Генератор CTA (4.5) —
`build_post()` напрямую вызывает `generate_cta_variants()` для секции CTA,
без HTTP-запроса. CTA-цель выводится из типа поста (продающий → «купить»,
анонс → «подписаться», новость → «перейти по ссылке», личный → «написать
в личку»). Тон в CTA задаёт только текстовую обёртку (без эмодзи в самой
фразе) — 2-3 фирменных эмодзи из Brand Kit добавляет исключительно 4.1 в
самом конце поста, чтобы не задваивать эмодзи с "зашитыми" в тон.

Приветствие (4.2) и заголовок правил (4.3) оборачивают ключевые слова в
`*bold*` — это настоящий Telegram legacy Markdown (один астериск), а не
канонический `**bold**` редактора Markdown Builder (Этап 2) — то есть
текст можно сразу отправлять ботом с `parse_mode="Markdown"`, без
дополнительного экспорта.

Сохранение — как и в Этапах 2-3, через универсальный
`POST /api/projects/:id/history`, отдельных per-модульных эндпоинтов нет.
Headline Generator и CTA Generator сохраняют по клику на конкретном

## Про использование базы CodeNexa для тестов

Таблицы этого проекта (`users`, `projects`, `brand_kits`, `generated_items`,
`templates`) не пересекаются по именам с таблицами CodeNexa — значит
`migrations/001_init.sql` можно безопасно прогнать на той же Supabase-базе,
что использует Codenexa2, для тестов/разработки. Для полноценного прод-
окружения в будущем рекомендуется отдельная база — Toolkit и CodeNexa не
должны шарить одну и ту же таблицу `users` (у них разная модель
пользователя: у CodeNexa есть роли/биллинг/OAuth, здесь — только
Telegram-профиль).
